Висновок:
За правилами C++ знакове переповнення int є невизначеною поведінкою (undefined behavior). Результат -2147483648 — це лише те, що сталося під час цього конкретного запуску, і він не є гарантованим. UBSan виявив переповнення та повідомив, що операція 2147483647 + 1 не може бути представлена типом int.
Водночас переповнення беззнакового байта є визначеною поведінкою в C++. Після збільшення значення 255 на 1 байт переходить до 0, а не до 256.

### §2. Переповнення: wrap vs UB
Беззнакове 8-бітне число після переповнення переходить від 255 до 0. Це визначенна поведінка в С++. Переповнення знакового 'int' є невизначенною поведінкою, тому UBSan виявив помилку та повідомив про неї. (див.M4 Exp 1)

### §3. Числа з рухомою комою
Більшість десяткових дробів не мають точного представлення в двійковому вигляді. Тому результат 0.1+0.2 при виведенні округлюється до 0.3, але при точному порівнянні (0.1 + 0.2 == 0.3) вийшло false. (див. M4 Exp 2)

### §4. Символ — це теж число
Результат:
```text
mk_@home-pc:~/pf/ember/characters$ ./characters
65 65 65 A
B
2 2.5
```
Висновок:
Експеримент показав, що символи можуть бути представлені числами. Наприклад, символ 'A' має числовий код '65'. Результат ділення залежить від типів операндів: якщо обидва операнди цілі, C++ відкидає дробову частину, тому '5 / 2 = 2'. Якщо один з операндів є числом з рухомою комою, дробова частина зберігається, тому '5 / 2.0 = 2.5'.

## Lab 02 - Results
### M1 - ALU як функції 
На першому етапі реалізовано ALU - арифметико-логічний пристрій, який виконує арифметичні та побітові операції над 8-бітними значеннями типу `Byte`(`uint8_t`)

Реалізовані операції:
`ADD` - додавання;
`SUB` - віднімання;
`AND` - побітове І;
`OR` - побітове АБО;
`XOR` - виключне АБО;
`NOT` - побітове заперечення;
`SHL` - зсув бітів вліво;
`SHR` - зсув бітів вправо;
`INC` - збільшення значення на 1;
`DEC` - зменшення значення на 1;

Прапорці ALU
Після виконання операції ALU встановлює прапорці:
`Z` (Zero) - дорівнює 1, якщо результат операції дорівнює 0;
`N` (Negative) - дорівнює 1, якщо старший (7-й) біт результату дорівнює 1;
`C` (Carry) - використовується для перенесення або позики при арифметичних операціях та для біта, що випадає після зсуву.

Приклад 1 - ADD з переповненням
```text
ember> set 0 0x10
ember> reg a 200
ember> reg b 100
ember> step
ember> regs
PC=1 A=44 B=100 Z=0 N=0 C=1
```
Математично `200 + 100 = 300`
Але оскільки `Byte` може зберігати значення лише від 0 до 255. Відбувається 8-бітне загортання: `300 = 256 + 44` 
Отже результат `44` записався в регістр `А`, а прапорець `С` змінився на 1 через переповнення.

Приклад 2 - SUB із запозиченням
```text
ember> set 0 0x11
ember> reg a 30
ember> reg b 100
ember> step
ember> regs
PC=1 A=186 B=100 Z=0 N=1 C=1
```
Математично `30 - 100 = -70`
Але `Byte`- це `uint8_t`, тобто він не зберігає знак значення. Відбувається 8-бітне загортання: `256 - 70 = 186`
Отже результат `186` записався  в регістр `А`, прапорець `С` вказав на запозичення, а прапорець `N` на старший біт результату.

Приклад 3 - AND і SHL
```text
ember> set 0 0x12
ember> reg a 12
ember> reg b 10
ember> step
ember> regs
PC=1 A=8 B=10 Z=0 N=0 C=0
```
Команда AND порівнює біти на однакових позиціях. Результат біту буде 1 тільки тоді, коли обидва біти дорівнюють 1. Що відбулось при виконанні step у двійковому вигляді:
12 = 00001100
10 = 00001010
AND= 00001000 = 8
Отже результат `8` записався в регістр `А`.


```text
ember> set 0 0x16
ember> reg a 128
ember> step
ember> regs
PC=1 A=0 B=0 Z=1 N=0 C=1
```
Команда SHL зсуває біти в байті на один вліво. Що відбулося у двійковому вигляді:
128 = 10000000 << 1
SHL = 00000000 = 0
Отже результат `0` записався в регістр `А`. Крайній лівий біт `1` випадає, тому загорається прапорець `С`.

### M3 - Програма, яку видно

На третьому етапі перевірено виконання послідовності інструкцій, записаних у пам'яті. Процесор за допомогою `PC` послідовно переходить між адресами пам'яті, а команда `step` виконує по одній інструкції.

Приклад 1 - AND і HALT

У регістри було записано `A=7` і `B=1`. У пам'ять за адресою 0 записано `AND` з опкодом `0x12`, а за адресою 1 — `HALT` з опкодом `0x00`.

```text
ember> reg a 7
ember> reg b 1
ember> set 0 0x12
ember> set 1 0x00
ember> regs
PC=0 A=7 B=1 Z=0 N=0 C=0

ember> step
ember> regs
PC=1 A=1 B=1 Z=0 N=0 C=0

ember> step
ember> regs
PC=2 A=1 B=1 Z=0 N=0 C=0

ember> step
CPU is halted.
ember> regs
PC=2 A=1 B=1 Z=0 N=0 C=0
```

Перший `step` виконав інструкцію `AND`, яка знаходилась за адресою `PC=0`.

У двійковому вигляді:

`7 = 00000111`  
`1 = 00000001`
`AND = 00000001 = 1`

Отже, результат `1` записався в регістр `A`, а `PC` перейшов з 0 на 1.

Другий `step` виконав `HALT` за адресою `PC=1`. Після цього процесор зупинився, а `PC` перейшов на 2. Наступний `step` вже не виконав нову інструкцію та вивів `CPU is halted.`.

Приклад 2 - трасування програми з трьох інструкцій

Для трасування було створено програму з трьох послідовних інструкцій `SHL` та `HALT`. Початкове значення регістра `A=32`.

У пам'ять записано:

`mem[0] = 0x16` — `SHL`  
`mem[1] = 0x16` — `SHL`  
`mem[2] = 0x16` — `SHL`  
`mem[3] = 0x00` — `HALT`

Результат виконання:

```text
ember> set 0 0x16
ember> set 1 0x16
ember> set 2 0x16
ember> set 3 0x00
ember> reg a 32
ember> regs
PC=0 A=32 B=0 Z=0 N=0 C=0

ember> step
ember> regs
PC=1 A=64 B=0 Z=0 N=0 C=0

ember> step
ember> regs
PC=2 A=128 B=0 Z=0 N=1 C=0

ember> step
ember> regs
PC=3 A=0 B=0 Z=1 N=0 C=1

ember> step
ember> regs
PC=4 A=0 B=0 Z=1 N=0 C=1

ember> step
CPU is halted.
ember> regs
PC=4 A=0 B=0 Z=1 N=0 C=1
```

Трасування програми:

| PC до `step` | `mem[PC]` | Інструкція | A після `step` | Z | N | C |
|---|---|---|---:|---:|---:|---:|
| 0 | `0x16` | `SHL` | 64 | 0 | 0 | 0 |
| 1 | `0x16` | `SHL` | 128 | 0 | 1 | 0 |
| 2 | `0x16` | `SHL` | 0 | 1 | 0 | 1 |
| 3 | `0x00` | `HALT` | 0 | 1 | 0 | 1 |

На першому кроці `32` зсувається на один біт вліво і перетворюється на `64`.

На другому кроці `64` перетворюється на `128`. Старший біт результату дорівнює 1, тому встановлюється прапорець `N=1`.

На третьому кроці виконується ще один `SHL`. Число `128` у двійковому вигляді має вигляд `10000000`. Після зсуву вліво старший біт `1` виходить за межі 8-бітного значення:

`10000000 << 1 = 00000000`

Тому в регістр `A` записується `0`, прапорець `Z` встановлюється в 1, а біт, який випав при зсуві, встановлює прапорець `C=1`.

На четвертому кроці виконується `HALT`, після чого процесор припиняє виконання наступних інструкцій.

### M4 - Декодування опкоду

На четвертому етапі реалізовано функцію `decode(Byte)`, яка розділяє опкод на два поля: групу та індекс.

Один опкод займає 8 біт:

- старші 4 біти — `group`, тобто група інструкцій;
- молодші 4 біти — `index`, тобто номер конкретної інструкції всередині групи.

Для збереження результату декодування створено структуру:

```cpp
struct Decoded {
    Byte group;
    Byte index;
};
```

Функція `decode()`:

```cpp
Decoded decode(Byte op) {
    Decoded d;

    d.group = (op >> 4) & 0x0F;
    d.index = op & 0x0F;

    return d;
}
```

Група отримується за допомогою зсуву вправо на 4 біти та маски:

`(op >> 4) & 0x0F`

Індекс отримується за допомогою маски:

`op & 0x0F`

Наприклад, опкод `0x14` відповідає інструкції `XOR`.

У двійковому вигляді:

`0x14 = 0001 0100`

Після декодування:

`group = 0001 = 1`  
`index = 0100 = 4`

Отже, `decode(0x14)` повертає групу `1` та індекс `4`.

У функції `step()` результат `decode()` використовується в `switch`. Спочатку процесор визначає групу інструкцій:

```cpp
Decoded d = decode(op);

switch (d.group) {
    case 0:
        // HALT, NOP
        break;

    case 1:
        // ALU
        break;
}
```

Для групи `1` індекс визначає конкретну операцію ALU. Наприклад:

```cpp
switch (d.index) {
    case 0:
        cpu.a = ALU_ADD(cpu.a, cpu.b, cpu.f);
        cpu.pc++;
        return;

    case 1:
        cpu.a = ALU_SUB(cpu.a, cpu.b, cpu.f);
        cpu.pc++;
        return;

    case 4:
        cpu.a = ALU_XOR(cpu.a, cpu.b, cpu.f);
        cpu.pc++;
        return;
}
```

### Реалізовані інструкції ISA

У лабораторній роботі реалізовано виконання інструкцій груп `0x0_` та `0x1_`.

| Opcode | Інструкція | Опис |
|---|---|---|
| `0x00` | `HALT` | Зупиняє виконання процесора |

| `0x12` | `AND` | Виконує побітове AND |
| `0x13` | `OR` | Виконує побітове OR |
| `0x14` | `XOR` | Виконує побітове XOR |
| `0x15` | `NOT` | Виконує побітове заперечення `A` |
| `0x16` | `SHL` | Зсуває біти `A` на одну позицію вліво |
| `0x17` | `SHR` | Зсуває біти `A` на одну позицію вправо |
| `0x18` | `INC` | Збільшує `A` на 1 |
| `0x19` | `DEC` | Зменшує `A` на 1 |

Для ALU-операцій результат записується в регістр `A`. Після виконання операцій оновлюються прапорці відповідно до правил ISA.

## M1. Робота з 16-бітними значеннями

Оскільки пам'ять `ember` складається з байтів (`Byte`, 8 біт), одне 16-бітне значення займає **2 байти**.

### Порядок байтів little-endian

Використовується порядок **little-endian**: спочатку зберігається молодший байт (`lo`), а потім старший (`hi`).

Наприклад, число `0x1234` записується так:

| Адреса | Значення |
|---|---|
| `addr` | `0x34` — молодший байт |
| `addr + 1` | `0x12` — старший байт |

Для відновлення числа використовується формула:

```cpp
lo | (hi << 8)
```

### Перевірка меж пам'яті

У `set16()` додано перевірку, щоб запис двох байтів не виходив за межі масиву `Memory.data`.

Пам'ять `ember` має **4096 байтів** (адреси від `0` до `4095`). Тому остання допустима початкова адреса для запису 16-бітного значення — `4094`.

### Перевірка роботи

Для перевірки було створено тимчасову тестову програму `test16.cpp`.

Результати тестування:

| Перевірка | Результат |
|---|---|
| Запис `0x1234` | Молодший байт `0x34`, старший `0x12` |
| Читання записаного значення | `0x1234` |
| Запис за недопустимою адресою | `set16()` повертає `false` |

Усі перевірки пройшли успішно.

### Висновок

У M1 реалізовано читання та запис 16-бітних значень у порядку little-endian. Ці функції використовуються процесором для отримання 16-бітних адрес із машинних інструкцій.

## M2. Реалізація інструкцій процесора

### Що було реалізовано

У файлах `cpu.hpp` та `cpu.cpp` додано нові інструкції для роботи з регістрами, пам'яттю та виведенням даних.

У структуру `CPU` додано **16-бітний регістр `H`**, який зберігає адресу комірки віртуальної пам'яті.

### Інструкції

| Інструкція | Код | Призначення |
|---|---|---|
| `OUT` | `0x02` | Вивести значення A як символ |
| `OUTN` | `0x03` | Вивести значення A як число |
| `LOADI A/B` | `0x20–0x21` | Завантажити число безпосередньо в регістр |
| `LOAD A/B,[addr16]` | `0x22–0x23` | Прочитати байт із заданої адреси пам'яті |
| `STORE [addr16],A/B` | `0x24–0x25` | Записати байт за заданою адресою |
| `MOV A,B / MOV B,A` | `0x26–0x27` | Скопіювати значення між регістрами |
| `LOADH` | `0x28` | Завантажити 16-бітну адресу в H |
| `LOAD A,[H]` | `0x29` | Прочитати байт за адресою з H |
| `STORE [H],A` | `0x2A` | Записати A за адресою з H |
| `INCH` | `0x2B` | Збільшити H на 1 |
| `DECH` | `0x2C` | Зменшити H на 1 |

### Виконання інструкцій

Функція `step()` зчитує код інструкції з пам'яті за адресою `PC`, визначає її тип і виконує відповідну дію.

Залежно від інструкції лічильник команд `PC` збільшується на:

- **1 байт** — інструкція без додаткових даних;
- **2 байти** — інструкція з одним байтом даних, наприклад `LOADI`;
- **3 байти** — інструкція з 16-бітною адресою, наприклад `LOADH`.

Перед виконанням перевіряється, чи не виходить інструкція за межі пам'яті. Якщо виходить, процесор зупиняється.

### Перевірка роботи

**1. Запис у пам'ять через H**

Перевірено послідовність `LOADI A,77 → LOADH 0x800 → INCH → STORE [H],A → DECH → HALT`.

Результат:

```text
PC=9 A=77 B=0 H=2048 Z=0 N=0 C=0
```

Перевірка пам'яті:

```text
ember> get 2049
77  0x4d  0b01001101  'M'
ember> get 2048
0  0x0  0b00000000  '.'
```

Число 77 записано за адресою 2049. Після `DECH` регістр H повернувся до 2048.

**2. Пряма адресація пам'яті**

Перевірено `LOADI A,90 → STORE [0x800],A → LOADI A,0 → LOAD A,[0x800] → OUTN → HALT`.

Результат:

```text
ember> run
90 ember> regs
PC=12 A=90 B=0 H=0 Z=0 N=0 C=0
ember> get 2048
90  0x5a  0b01011010  'Z'
```

Після обнулення A число 90 було успішно прочитане з пам'яті назад у регістр.

### Висновок

У M2 реалізовано інструкції для завантаження, читання, запису та виведення даних. Додано адресацію через регістр H і перевірку меж пам'яті під час зчитування інструкцій. Основні операції перевірено тестовими програмами.

## M3. Запуск програми та трасування інструкцій

### Що було реалізовано

У файлі `main.cpp` додано команду `run`, яка запускає виконання програми у віртуальному процесорі.

На відміну від `step`, яка виконує одну інструкцію, `run` виконує інструкції послідовно до `HALT`.

Також додано обмеження у **10000 кроків**, щоб програма не виконувалася нескінченно, якщо процесор не досягне `HALT`.

### Перевірка виведення AB

Для тестування в пам'ять за адресою `0x800` записано символи `ABC` та завершальний нуль:

| Адреса | Значення | Символ |
|---|---|---|
| `0x800` | `0x41` | A |
| `0x801` | `0x42` | B |
| `0x802` | `0x43` | C |
| `0x803` | `0x00` | Завершальний нуль |

Програма складається із семи інструкцій:

| № | Інструкція | Дія |
|---|---|---|
| 1 | `LOADH 0x800` | Завантажити адресу 2048 у H |
| 2 | `LOAD A,[H]` | Прочитати символ A |
| 3 | `OUT` | Вивести A |
| 4 | `INCH` | Перейти до наступної адреси |
| 5 | `LOAD A,[H]` | Прочитати символ B |
| 6 | `OUT` | Вивести B |
| 7 | `HALT` | Завершити виконання |

**Результат виконання:**

```text
ember> run
ABember> regs
PC=9 A=66 B=0 H=2049 Z=0 N=0 C=0
```

Програма правильно вивела `AB`. Регістр H містить адресу другого символу, а A — його ASCII-код 66.

### Дамп пам'яті

Початок пам'яті з машинним кодом програми:

```text
0000  28 00 08 29 02 2b 29 02 00 00 00 00 00 00 00 00  |(..).+).........|
```

Дані за адресою `0x800`:

```text
0800  41 42 43 00 00 00 00 00 00 00 00 00 00 00 00 00  |ABC.............|
```

Код програми розміщений із адреси `0x000`, а дані — з `0x800`.

### Трасування семи інструкцій

Для перевірки покрокового виконання використано команди `step` і `regs`.

Тестова програма виконувала такі дії: завантаження чисел 5 і 3, додавання, завантаження адреси в H, збільшення та зменшення H, завершення роботи.

Отримані значення регістрів:

| Крок | Інструкція | PC | A | B | H |
|---|---|---:|---:|---:|---:|
| 0 | Початковий стан | 0 | 0 | 0 | 0 |
| 1 | `LOADI A,5` | 2 | 5 | 0 | 0 |
| 2 | `LOADI B,3` | 4 | 5 | 3 | 0 |
| 3 | `ADD` | 5 | 8 | 3 | 0 |
| 4 | `LOADH 0x800` | 8 | 8 | 3 | 2048 |
| 5 | `INCH` | 9 | 8 | 3 | 2049 |
| 6 | `DECH` | 10 | 8 | 3 | 2048 |
| 7 | `HALT` | 11 | 8 | 3 | 2048 |

Прапорці `Z`, `N` і `C` протягом усього тесту дорівнювали `0`.

### Висновок

У M3 реалізовано автоматичне виконання програми командою `run`. Перевірено виведення символів `AB`, розміщення програми й даних у пам'яті та правильну зміну регістрів під час покрокового виконання семи інструкцій.

## M4. Перевірка пам'яті за допомогою AddressSanitizer

### Що було зроблено

Для перевірки безпеки роботи з пам'яттю використано **AddressSanitizer (ASan)** — інструмент для виявлення помилок доступу до пам'яті.

У файлі `checks/asan_test.cpp` створено тест із навмисним виходом за межі масиву `Memory.data`.

Масив містить 4096 байтів, тому допустимі індекси — від `0` до `4095`. У тесті виконується звернення до індексу `4096`:

```cpp
volatile Byte value = mem.data[MEM_SIZE];
```

### Запуск перевірки

Тест скомпільовано з увімкненим AddressSanitizer:

```bash
g++ -g -O0 -fsanitize=address -fno-omit-frame-pointer checks/asan_test.cpp -o checks/asan_test
```

Після цього запущено:

```bash
./checks/asan_test
```

**Результат перевірки:**

```text
Memory size: 4096
=================================================================
==3314==ERROR: AddressSanitizer: stack-buffer-overflow
READ of size 1
SUMMARY: AddressSanitizer: stack-buffer-overflow checks/asan_test.cpp:10 in main
==3314==ABORTING
```

ASan виявив спробу прочитати один байт за межами масиву. Помилка знаходиться на 10-му рядку файлу `asan_test.cpp`.

Звіт перевірки зберігається у файлі `checks/asan-report.txt`.

### Різниця між вказівником C++ та адресою ember

**Вказівник C++** зберігає адресу об'єкта в пам'яті реального процесу.

**Адреса в `ember`** — це число, яке позначає комірку масиву `Memory.data`.

Наприклад, адреса `0x800` відповідає індексу `2048` у віртуальній пам'яті.

Регістр `H` зберігає саме віртуальну адресу, а не вказівник C++. Для доступу до пам'яті `ember` використовуються функції `mem_get()` і `mem_set()`.

### Висновок

У M4 перевірено роботу AddressSanitizer. Інструмент успішно виявив навмисний вихід за межі `Memory.data`. Також розглянуто різницю між реальною адресою пам'яті процесу та адресою у віртуальному комп'ютері.
